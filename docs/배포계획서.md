## 1. 구조와 배포 역할

아래 파일명은 별도 표시가 없으면 `kbo_comparison/` 기준입니다.

| 역할 | 판단 | 근거 |
| --- | --- | --- |
| A 정적 화면 | 해당. 정적 화면은 미리 준비한 파일을 그대로 내려주는 방식 | `index.html`, `scouting-dashboard.html`, `scouting-portfolio.html`에 화면이 있고 `app.js`, `dashboard.js`, `portfolio.js`가 브라우저에서 동작 |
| B 웹앱/API | 로컬 실행에 해당. API(프로그램이 데이터를 요청하는 창구)는 첫 공개에 불필요 | `server.py`는 `127.0.0.1:8000`에서 읽기 전용 `GET /api/players`를 제공. `repository.js`는 이 경로가 404/405를 반환하면 `data.js`와 `metadata.js`의 동봉 자료를 사용 |
| C 상시 연결 | 해당 없음 | 웹소켓(브라우저와 서버를 계속 연결해 두는 방식)이나 상시 연결 처리 코드가 실행 경로에 없음 |
| D 예약 작업 | 해당 없음 | `sync_data.py`는 CSV를 JSON과 브라우저 파일로 바꾸는 수동 작업. 자동 갱신 일정·외부 수집 연동이 없음 |
| E 데이터·데모 화면 | 해당 | `data.js`, `sample_data.json`, `data_metadata.json`, 원본 CSV 및 스카우팅 리포트. 홈런 기준선 보고서는 학습을 실행하지 않고 결과를 열어보는 데모 |
| F 비동기 분석 작업 | 현재 수동 실행 도구로 존재. 온라인 역할은 확장 시에만 추가 | `ml/evaluate_baseline.py`, `ml/predict_home_runs.py`, `ml/visualize_results.py`는 명령줄에서 실행. 웹 요청에서 호출하거나 상태를 저장하는 경로 없음 |

현재 메모는 `portfolio.js`의 `localStorage`(브라우저에 남는 작은 저장공간)에 저장됩니다. 주소, 브라우저 또는 프로필이 바뀌거나 사용자 데이터가 삭제되면 이전 메모를 읽을 수 없습니다. 로그인·공유용 데이터베이스·서버 권한 검사는 없습니다. CSV는 브라우저에서 만들고 PDF는 브라우저의 인쇄 기능으로 저장합니다. 외부 기사와 KBO 자료는 사용자가 여는 링크입니다.

입력 파일 업로드나 HTTP 요청(브라우저가 서버에 보내는 작업 요청) 안에서 영상 분석을 실행하는 기능은 없습니다. 상위 폴더의 영상, 약 566 MiB인 `people_detection/`, 모델 파일과 학습 결과는 별도 실습 자료입니다. `people_detection/train.py`와 `train_mps.py`는 YOLO(영상에서 물체를 찾는 모델)와 PyTorch(모델 학습 도구)를 사용합니다. CPU(일반 계산 장치) 또는 Apple MPS(애플 그래픽 장치를 쓰는 방식)로 실행하며, 그 코드와 공개 화면의 연결은 없습니다. 현재 배포 경로에 OpenCV(영상 처리 도구)·FFmpeg(영상 변환 도구) 호출은 없습니다. 향후 영상 기능은 별도로 입력 형식과 변환·분석 도구를 정하고 측정합니다. `DESIGN-mongodb.md`, `guestbook-setup.sql`은 상위 폴더에 있으며 이 웹사이트 실행 경로에는 연결되지 않습니다.

향후 오래 걸리는 분석을 온라인으로 제공할 때의 흐름입니다. Worker(화면과 분리되어 작업을 처리하는 실행 프로그램)는 첫 배포에 만들 필요가 없습니다.

```text
화면 → API 접수 → 작업 ID와 제한 시간 업로드 주소 발급
  ├─ 파일 → 객체 저장소(대용량 파일 보관 공간)에 직접 업로드
  └─ 업로드 확인 → 작업 대기열 → CPU 또는 GPU Worker
                                  ├─ 결과 파일 → 객체 저장소
                                  └─ 진행 상태·결과 주소 → DB → 화면에서 조회
```

API는 소유자와 파일 조건을 확인한 뒤 작업 ID를 반환합니다. 작업 상태는 접수·실행 중·완료·실패로 남깁니다. 대기열에는 파일 자체 대신 ID를 넣고, 같은 ID로 재시도해도 결과가 중복되지 않도록 합니다. GPU(병렬 계산에 강한 그래픽 장치)로 이전할 때도 화면·업로드·상태 기록 흐름은 그대로 쓸 수 있습니다.

## 3. 분석 1회 자원 대시보드

**대표 작업**은 스카우팅 포트폴리오의 2024년 200타석 이상 전체 포지션 후보 분석입니다. 브라우저와 같은 `analytics.js`, `portfolio-model.js`로 자료를 읽고 출루형 순위를 매긴 뒤 장타형으로 비중을 바꿔 순위 변화를 계산했습니다. 실제 선수 기록 대신 입력 행 수를 맞춘 가상 기록 10,209행(측정 2,467,320바이트, 약 2.35 MiB)을 사용했고, 가상 후보 232명의 결과를 검증했습니다. 로컬 저장을 건드리지 않고 임시 폴더에서 준비 1회 후 별도 프로세스로 3회 실행했습니다.

**환경·명령**은 2026-11-21 KST, Apple M5 10코어/16 GB, macOS 27.2.1 ARM64, Node.js 26.13.1입니다. 작업 폴더에서 아래 명령으로 재현할 수 있습니다. 브라우저 렌더링, 파일 다운로드와 모바일 환경은 측정에 포함되지 않았습니다.

```sh
plan_tmp=$(mktemp -d /tmp/kbo-plan.XXXXXX)
cat > "$plan_tmp/bench.cjs" <<'BENCH'
const fs = require('node:fs');
const {performance} = require('node:perf_hooks');
const [root, work, mode] = process.argv.slice(2);
if (mode === 'prepare') {
  const rows = Array.from({length:10209}, (_,i) => {
    const j=i%232, AB=270+j, H=65+j%75, HR=j%33;
    return {Id:String(10000+j),Player:'가상선수'+j,Born:'1990-01-01',
      Age:30,Season:1982+Math.floor(i/232),Team:['삼성','롯데','LG','KIA'][j%4],
      Position:'1B',G:100,PA:AB+45,AB,H,HR,TB:H+3*HR+25,BB:40,
      HBP:2,SF:3,SO:45+j%70,'2B':16,'3B':2,SB:1+j%19,CS:j%7,RBI:45,R:55};
  });
  fs.writeFileSync(work+'/input.json',JSON.stringify(rows));
  process.exit();
}
const A=require(root+'/analytics'), P=require(root+'/portfolio-model');
const cpu=process.cpuUsage(), start=performance.now();
const data=JSON.parse(fs.readFileSync(work+'/input.json','utf8'));
const pool=P.poolFor(A.create(data),2024,'',200);
const rankings=P.evaluate(pool,P.presets.onbase);
const mix=P.sensitivity(pool,P.presets.onbase,P.presets.power);
if (pool.length!==232 || rankings.length!==232 || mix.length!==232 ||
    !Number.isFinite(rankings[0].value)) throw Error('unexpected output');
const d=process.cpuUsage(cpu);
console.log({wallMs:performance.now()-start,cpuMs:(d.user+d.system)/1000,
  peakRssKiB:process.resourceUsage().maxRSS,rows:pool.length});
BENCH
node "$plan_tmp/bench.cjs" "$PWD/kbo_comparison" "$plan_tmp" prepare
node "$plan_tmp/bench.cjs" "$PWD/kbo_comparison" "$plan_tmp" >/dev/null
for repeat in 1 2 3
do
  /usr/bin/time -lp node "$plan_tmp/bench.cjs" "$PWD/kbo_comparison" "$plan_tmp"
done
wc -c "$plan_tmp/input.json"
```

홈런 모델 측정 명령은 `/usr/bin/time -lp python kbo_comparison/ml/predict_home_runs.py --csv "<가상 CSV 경로>" --through-season 2025 --output-dir "<임시 결과 경로>"`입니다. `ml/requirements.txt` 설치 후 준비 실행을 빼고 3회 측정합니다. 기준선은 같은 방식으로 `evaluate_baseline.py`를 실행합니다. 향후 영상은 규격을 정한 가상 영상으로 CPU와 GPU를 각각 세 번 측정합니다. 입력·임시·출력 용량과 GPU 시간을 따로 기록할 필요가 있습니다.

동시 실행은 검증하지 않았습니다. 선형 추정식은 `N × 0.1132초 CPU`, `N × 112.6 MiB`, 순차 마지막 완료 `N × 0.06476초`입니다. 이는 서버 메모리 요구량이 아니며 기기 성능, 첫 다운로드, 화면 그리기, 네트워크 지연은 포함하지 않습니다. 클라우드에서 홈런 학습·영상을 수행할 경우 대기시간은 미측정입니다.

| --- | --- | --- | --- | --- |
| 100회 | 추정 US$0 | 추정 US$0 | 추정 US$0 | 추정 US$0 |
| 1,000회 | 추정 US$0 | 추정 US$0 | 추정 US$0 | 추정 US$0 |
| 10,000회 | 추정 US$0 | 추정 US$0 | 추정 US$0 | 추정 US$0 |

식은 `첫 정적 호스팅 US$0 + N × 브라우저 계산·API·DB 비용 US$0`입니다. 기본 주소, 판매세·별도 도메인 제외 기준입니다. 정적 파일 요청에는 횟수 요금이 없어 위 분석 횟수 자체가 무료 한도를 넘기지 않습니다. 초과 지점은 월 500회 게시 작업, 20,000개 사이트 파일 또는 파일당 25 MiB 등 프로젝트의 게시 한도입니다.

추후 CPU 작업 비용의 별도 예시는 미국 중부 기준 1 vCPU(서버가 할당하는 CPU 단위), 512 MiB에 1분 이내 종료하는 짧은 작업입니다. **홈런 학습이나 영상 작업의 견적은 아닙니다.** 실행 건별 최소 60초 과금에 따라 `CPU초=60N`, `메모리 GiB초=30N`으로 계산합니다. 다른 사용이 무료 한도를 쓰지 않았다면 100회·1,000회는 작업 실행료 추정 US$0, 10,000회는 `(600,000−240,000) × US$0.000018 = US$6.48`입니다. 메모리 300,000 GiB초는 무료 한도 안입니다. CPU는 4,001회, 메모리는 15,001회부터 해당 항목의 초과가 시작됩니다. 외부 API 추정 US$0이며, 예시에는 상태 DB·저장소·추가 읽기·로그·배포용 이미지 저장료를 넣지 않았습니다. 이를 사용하는 실제 온라인 확장비는 파일량과 보관기간을 정한 뒤 별도로 산정합니다. [Cloud Run 공식 가격](https://cloud.google.com/run/pricing)

- **최소 사양**은 정적 호스팅과 사용자 브라우저 CPU입니다. 별도 서버 사양을 구매할 필요가 없습니다.
- **쾌적 사양**은 모바일에서 첫 진입을 검사하고 데이터와 이미지 다운로드를 줄이는 구성입니다.
- **병목**은 계산보다 수 MiB의 자료·이미지 초기 전송일 가능성이 있습니다. 모바일 실측으로 확인합니다.

지금 가장 저렴한 CPU안은 사이트 분석은 브라우저, 홈런 실험은 운영자의 로컬 CPU입니다. 온라인 반복 실행이 필요해지면 CPU Jobs에서 메모리 부족 여부와 대기시간을 먼저 확인합니다. `predict_home_runs.py`의 scikit-learn Random Forest(여러 결정 트리를 결합하는 모델)는 현재 CPU 단일 작업 슬롯으로 구성되어 있어 L4에 연결해도 자동으로 빨라지지 않습니다. 영상처럼 GPU를 지원하는 작업이 생겨 CPU가 합의한 대기시간을 반복적으로 넘기거나 GPU 사용 시 결과 한 건당 비용이 실제로 줄 때만 영상 분석 프로그램을 GPU Worker로 옮깁니다. Apple MPS로 고정된 경로는 장치 선택을 설정으로 분리하고 NVIDIA용 PyTorch 환경에서 검증합니다. [Cloud Run GPU 작업 설정](https://docs.cloud.google.com/run/docs/configuring/jobs/gpu)

## 8. 배포 순서

1. 게시 사본과 자료 공개 권한을 확정하고, 화면·허용 데이터·필요 이미지 및 공개 승인된 데모만 별도 폴더에 모읍니다. 첫 구성에는 별도 컴파일이나 패키지 설치가 없습니다.
2. 로컬 확인은 상위 폴더에서 `python3 kbo_comparison/server.py`로 하고 `http://localhost:8000`을 엽니다. `node --test kbo_comparison/tests/*.test.js`와 `PYTHONDONTWRITEBYTECODE=1 python3 kbo_comparison/tests/test_server.py`를 실행합니다. 데이터 갱신 시에만 `python3 kbo_comparison/sync_data.py`로 동봉 파일을 맞춥니다.
3. 실제 공개를 승인받은 뒤 Pages의 직접 업로드로 시험 주소를 만들고, 아래 체크리스트를 통과하면 기본 제공 공개 주소를 사용합니다.
4. 홈런 모델을 서비스에 보여줄 경우 운영자 CPU에서 데이터를 검증하고 결과를 먼저 만들어 공개 여부를 검토합니다. 의존성은 `ml/requirements.txt`에 있으며 검증 명령은 `python -m unittest discover -s kbo_comparison/ml -p 'test_*.py' -v`입니다. 모델 테스트가 건너뛰어졌는지 확인합니다.
5. 사용자별 분석이 필요해지면 비공개 파일 저장소, 인증된 접수, 상태 DB, 대기열과 CPU Worker를 연결합니다. 가상 입력으로 1·5·10명 동시 제출과 실패 재시도를 검증한 뒤 실행 상한과 비용 알림을 정합니다.
6. 실제 영상 기능에서 처리 시간이나 건당 비용 목표가 필요해질 때 GPU를 시험하고, 개선이 확인된 영상 실행 부분만 CPU Worker에서 분리합니다.

| 업로드 주소 만료 또는 다른 사용자가 조회 가능 | 확장 시 API 권한 검사와 저장소 기록 | 소유권 확인 후 짧은 기간의 주소를 재발급. 비공개 저장 정책과 작업별 접근 제어 확인 |
| 처리가 오래 걸리거나 중복 실행 | 확장 시 대기열·작업 실행 기록·상태 DB | 중복 방지 키, 제한 시간, 재시도 횟수와 동시 실행 수 설정. 실제 처리량을 보고 조정 |
| 예상 밖 과금 | 결제 사용량·예산 알림·저장 보관 상태 | 알림은 자동 정지를 보장하지 않으므로 작업 접수량과 동시 실행 한도도 설정. 실패 재시도와 파일 보관 기간 확인 |

## 10. 배포 후 체크리스트

- [ ] 기본 제공 주소와 HTTPS(통신 내용을 암호화하는 연결) 및 각 하위 화면 직접 접속을 확인합니다.
- [ ] 선수 찾기·기록 비교·스카우팅·부상 출처·CSV 다운로드·PDF 저장을 확인합니다.
- [ ] 휴대전화에서 초기 로딩, 가로 표, 접기 메뉴 확대, 보고서 줄바꿈을 확인합니다.
- [ ] 새로고침, 같은 주소 재접속, 다른 브라우저 접속을 비교해 메모 보관 범위를 확인합니다.
- [ ] 공개 파일 목록과 공개 권한을 확인하고, 비공개 자료나 키가 내려받아지지 않는지 확인합니다.
- [ ] 확장 시 브라우저 직접 업로드, 만료 주소, 파일 크기 제한, 다른 사용자 작업 차단을 확인합니다.
- [ ] 확장 시 Worker 완료·실패·재시도·중복 방지 및 종료 후 결과 유지를 확인합니다.
- [ ] 게시 사용량과 데이터 전송을 확인하고, 유료 기능을 켜면 CPU·메모리·저장 용량 및 비용 알림을 확인합니다.
